# Vikix Dependable — design

The laptop Vid works on as something to depend on: updates to trust and undo, breakage caught before it costs time, agents left running unattended in safety, and a machine that stays fast.

Drafted 2026-10-18 from Groki's handover (its "Distro-level improvements"), from reading the code at 0.72.95 and not yet checked on the machine. Written for Vid alone: Vikix has no other users yet, so the aim is less time lost to a broken machine, a stuck release or an agent to babysit, not a promise to anyone else. Where an item is already a TODO, it is named and not repeated; the notes marked *2026-10-18* are what Vikix already has, from the code. Kept honest like the other designs: what ships is deleted here, what changes is dated.

---

## Updates to trust and undo

Do these first: they make every other change safer.

1. **A known-good channel for the laptop.** Main moves about twenty times a day, and agents release with no gate (`plans/music-next.toml` releases by the plan, no user gate). `vikix update` follows a `good` tag that moves only after CI is green, plus a quick local smoke test. Development stays on main; the machine Vid works on takes only green releases. *2026-10-18:* `gup` (`repos ship`) pushes and then runs `vikix update core` at once, before CI has run, so this changes the usual step after a release too. *2026-10-21:* in part. The `good` job in `.github/workflows/test.yml` moves the tag after the three jobs pass on main; `~/.config/vikix/channel` (`good` by default, `main` for the machine Vid develops on: the Z13, by his choice, so `gup` stays one step) is followed by `vikix update core` (`pull_channel`) and by the bar's count (`bin/vikix-updates`). *2026-10-22:* the rest is in. A core update ends with a check before it is called a success (`update_check` in `cmd_update`; `vikix update check` alone): the StumpWM image asked whether it starts (`VIKIX_WM_CHECK`, no screen; an image from before the question is left alone, said), the three links into the checkout, and the doctor, whose findings are counted and listed but don't fail it (they may be older than the update); an image that doesn't start or a link astray ends the update in failure, with `vikix update --back` named. On the main channel `vikix-updates` asks GitHub's public API (no key) for the test workflow's verdict on the commit the machine runs, a fourth word in its file (ok, failed, running, ?; `-` on good, where nothing is asked), every ten minutes while a run is going; the bar says `tests failed` in front of the counts, and a notification says it once per commit. `tests/update.sh`, `tests/updates.sh`, `tests/try.sh`. Left: nothing planned; a bad commit seen for real on the Z13 will say whether ten minutes is right.
2. **System rollback** (TODO 6, *Whole-system undo*, widened). `vikix undo` covers the user's files only. Before `vikix update`, a root snapshot (btrfs and snapper where the disk allows), or at least a record of the xbps package set and the StumpWM binary, so `vikix update --back` brings the last good state back in one step. *2026-10-20 (0.72.124, `bin/vikix-rollback`):* in, the record form: `keep` before the pull (commit, version, `xbps-query -l`, the StumpWM binary once per hash), `keep packages` before `xbps-install -Su` (what `-Sun` says will change, their current files copied from `/var/cache/xbps`, the ones not there named), the two newest records; `restore` checks the commit out, runs 40-config, copies the binary back, indexes the kept files and reinstalls them with `-f`; snapper's snapshot and rollback line on btrfs, written but not tried (no btrfs here). *2026-10-21:* restore tried for real on the Z13 after a hand-broken binary: checkout, 40-config and binary back in 5.5 s (`plans/DESKTOP-1.0.md`, gate A evidence); package reinstall not yet exercised for real.
3. **The Lisp toolchain pinned.** *2026-10-21:* in. `QL_DIST` in `install/30-lisp.sh` pins the Quicklisp release (2026-01-01); a fresh install gets it, and `lib/build-stumpwm.lisp` moves `~/quicklisp` to it before a build at another. SBCL stays Void's (a held package would leave the system half updated); the build is noted instead (`~/.local/state/vikix/stumpwm-built`: when, Vikix's commit, SBCL, the dist), which `vikix doctor` reads. A rebuild asks the new image whether it starts (`VIKIX_WM_CHECK`: it loads, says so and exits, no X) and throws it away when it doesn't; the one before stays as `stumpwm.prev`, and `vikix-session` starts that when the new one dies within twenty seconds, with a notification and a note the doctor shows. `tests/lisp-stage.sh`, `tests/session.sh`; the real build tried once on the X1 (the image answers the check). Left: TODO 92's dumped core will want the same fallback; the fallback itself has not yet run at a real login.
4. **Signed updates** (To look into 4; `DESIGN-security.md` item 1; TODO "What's next" 3). `vikix update` verifies a signed tag before running any stage with sudo. On 2026-10-04 Vid put this off until the first outside user; the handover argues it matters now because agents can land on main without him. Less urgent than 1 to 3. **For Vid to decide** whether that changes the 2026-10-04 call.

## Catch breakage before it costs time

5. **An update doctor.** After `vikix update`, and when asked: the runit services, that the StumpWM image loads, PipeWire, the network and the battery, then one notification: all well, or exactly what broke and the fix. (`vikix doctor` checks much of this already; TODO 103's `--fix` is the mending half.) *2026-10-22:* the first half is item 1's check: a core update ends by asking the image and running the doctor, saying what it found in the terminal, where `gup` is watched; the notification is left for when an update runs unattended. The mending half is in the same day: `vikix doctor --fix` (TODO 103, `ARCHIVE.md`).
6. **A hardware check for this laptop.** `vikix-hwreport` and a small script for suspend and resume, the lid, the brightness keys, sound out and in, and the touchpad, to run after an update or a kernel change. *2026-10-18:* `vikix-hwreport` is the stick's (`installer/vikix-hwreport`), not in `bin/`; it would come over.
7. **Feedback in tiers.** A set that finishes in under five minutes before a release (tighter than today's `tests/run.sh --quick`), with the full set run at night while the laptop is idle and failures reported in the morning. Goes with `DESIGN-ci.md` item 3: the load gate, the weighted slots, once more alone.

## Run more agents unattended, safely

8. **Keys only where needed.** `lib/secrets.sh` and `vikix.bash` export the API keys into every shell; that is what broke `tests/docs.sh` (`DESIGN-ci.md`). Instead `vikix key run CMD`, or a wrapper a tool, giving each tool only the key it needs. (Gap E of `DESIGN-security.md` is the same folder.)
9. **Desks enforced by the system.** The house rules are hooks only (Claude Code, Codex, OpenCode, Antigravity), and `protection_lines` says so: no filesystem enforcement. Run an agent's session under bubblewrap or Landlock with only its desk and scratch folders writable; then any agent, and anything it starts, is held, and Vid can leave more of them running overnight. (Beside TODO 97's permission list and TODO 99's advisory locks; IDEAS has bubblewrap for `vikix try PROGRAM`.)
10. **The outbound ledger** (TODO 81, `DESIGN-security.md` item 8): what left the machine, when and to whom, for a quick look each morning.
11. **Releases and agents in one view.** A bar field or an Office pane: the release queue, which desk holds the release lock, who holds the test slots, the load, CI's state for the last push, and the GitHub branches not on main. It replaces asking "what is running?". *2026-10-18:* `.claude/release --queue` (`gq`) and the Office's Releases box show the queue and the steps already; the rest is new. (TODO 43, build status in the bar, is the CI part as a plugin.)
