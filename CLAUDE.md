# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Vikix is an opinionated desktop layer for **glibc Void Linux** built around **StumpWM**: Void, supercharged. It was inspired by Omarchy but is its own thing: credit Omarchy as the inspiration, but don't call Vikix "Omarchy for Void". It is not a distribution; it's a set of bash install stages run on top of a plain Void install, plus the config it puts in place and a `vikix` command that keeps it current. Repo: github.com/vukini/vikix (MIT).

This repo lives in `~/src/vikix` on the dev machine (until 2026-10-01 it was inside the Obsidian vault, `~/General/Living-in-Life/vikix`). The `vikix-*.zip` files are old releases and are gitignored.

**Edit in this repo (in a worktree of it: see Working in parallel), never in `~/vikix`.** This repo is where Vikix is developed. `~/vikix` on the dev machine is the installed checkout: it only pulls from GitHub, to see Vikix the way a user does. Don't edit, commit or stash there; `vikix update` sets edits aside and stops on commits. To try a change on the desktop, commit it here, push, and run `vikix update` (the `gup` alias does both).

`site/` is the website, vikix.dev: static pages (`index.html`, `gallery.html`) sharing `site.css`, screenshots in `site/shots/` (each scene as `NAME-void.webp` and `NAME-paper.webp`, 960px copies in `small/`), and `install`, the one-line install (`curl -fsSL https://vikix.dev/install | bash`: checks, clones, runs install.sh; one function called on the last line, so a cut-off download runs nothing), no build of its own, published by `.github/workflows/pages.yml` on each push that touches `site/`, `VERSION` or the guides (the workflow writes `VERSION` into the page, and builds `docs/` into `site/guide/`, vikix.dev/guide/, with `lib/build-guide.sh --site`; that folder is gitignored, never committed). When a release adds something a visitor would care about (a key, a feature card), update the page in the same commit.

`docs/` holds the user's guides (the map of files, how it fits together, customizing, fixing). They name real paths, keys, variables and commands: when a change moves or renames one, update the guide in the same commit. `40-config` also makes them an Info manual, `~/.local/share/info/vikix.info` (`info vikix`, Emacs `C-h i`), through `lib/md2texi.py`, which knows only the Markdown the guides use; It also makes them web pages, `~/.local/share/vikix/guide/` (`lib/build-guide.sh`: `makeinfo --html`, styled by `docs/guide.css`), and the same pages are the site's guide, vikix.dev/guide/, so a change to `docs/` reaches the site on its next push. Diagrams are `![what it shows](diagrams/NAME.svg)` on a line of their own, three files in `docs/diagrams/`: `NAME.mmd` (Mermaid source), `NAME.svg` (committed, drawn by `docs/diagrams/render.sh` with the system Chromium, ending with the source's SHA-1) and `NAME.txt` (the plain-text version Info shows). `tests/info.sh` fails on a broken link, a page missing from `docs/README.md`'s table, a makeinfo warning, a diagram missing a file, or an SVG not drawn from its current source. The `explainer` agent (`.claude/agents/explainer.md`) writes and keeps the guides and diagrams. `.claude/docs-check` (cron, Mondays at 10 on the dev machine) looks for guides gone stale: the plugins guide against the plugins repo (a section, every key, every setting), and commits since the last review that changed `bin/`, `config/`, `install/`, `packages/` or a plugin without the guides. It asks Vid in a dialog first; only on his yes does Claude Code open with what it found. Update the guides then with the explainer, show Vid the changes before committing, and finish with `.claude/docs-check --reviewed`.

**Every `bin/vikix*` starts with a header in one shape,** and three things are made from it: `-h` prints it (`sed -n '2,/^$/p'`, or the docstring), `vikix help` prints `bin/vikix`'s, and `lib/man.py` turns it into the command's man page (`40-config` writes them to `~/.local/share/man/man1/`; `MANPATH` is set by `vikix-session` and `vikix.bash`, since Void's `man`, mandoc, doesn't look beside `~/.local/bin`). The shape: `# vikix-NAME — one line`, then indented usage lines, `vikix NAME sub ARGS`, two spaces or more, `what it does` (further lines of it indented deeper), then prose; an indented block that doesn't start with the command is shown as it is. So a new command or option is documented by editing the header, nowhere else. `tests/lint.sh` fails a header out of shape (`python3 lib/man.py --check` says why); `python3 lib/man.py --page bin/vikix-NAME | mandoc | less` shows a page while writing. Two more things come from the same headers. `docs/commands.md` is them as a guide page, committed: **after changing any header, run `python3 lib/man.py --guide > docs/commands.md`**, or `tests/man.sh` fails; never edit that file by hand. And the commands of the plugins in the user's list get pages as well (`man inbox`): `lib/man.py` reads `~/.config/vikix/plugins.list`, `vikix plugin add`, `remove` and a moved pin run it again, a plugin's header out of shape only costs that page, and the plugins repo's `tests/check.sh` checks the shape (`python3 lib/man.py --check PLUGIN/bin`). It never writes over a page it didn't make.

`TODO.md` lists planned features and cleanups. Read it when asked what's next, and remove an item in the commit that ships it. `TUTORIALS.md` is the plan for `vikix learn` (a C course first). `IDEAS.md` holds ideas not yet decided on; one moves to `TODO.md` when it is picked up. `bugs.md` lists small known problems not yet fixed (what happens, what's known, the next step); a fix removes its entry. `TODO-editors.md` is the plan for the editors: Neovim's config into Vikix, and AI in Neovim and Emacs. `TODO-Windows.md` is what's left for Windows programs in their own windows (`vikix windows app`). `ai-desktop.md` is the plan for the AI desktop at work (one Radeon AI PRO R9700), beside the ROG Flow Z13 (TODO items 58–63). `DESIGN-*.md` are worked-out designs waiting to be picked up (`DESIGN-music.md` the musical sketchpad, `DESIGN-docs.md` the docs catalogue and the `vk` alias, `DESIGN-viri.md` the scrolling workspace, Phase 0 built as `viri.lisp`, `DESIGN-cuis.md` Cuis Smalltalk as a Vikix feature with a door for the agent, `DESIGN-publish.md` books, sites and EPUBs built and checked by one command, `DESIGN-security.md` the pen-tester's open findings as a dated plan: signed updates, pinned installers, the door module and allow-list, the ledger, `DESIGN-machines.md` your laptops, desktop and phones as one Vikix: Tailscale, Syncthing, KDE Connect, export/import and --on NAME, `DESIGN-restore.md` any file as it was: a file's versions from the backups and the snapshots, brought back as an Esploro plan, `DESIGN-site.md` the Living Series site in place of Substack: static pages from `vikix publish` on Cloudflare, a small Lisp gate on a Debian droplet for purchases and logins, Listmonk, a fan-out from the feed, `DESIGN-remoteapp.md` a Windows program's own window on the desktop, through RDP's RemoteApp); each moves to `TODO.md` when work starts, as Esploro's did. `APP-IDEAS.md` lists programs worth trying, with whether Void packages them. `NOVEL.md` holds the ideas no other desktop does, kept apart so they aren't lost among the small ones; it is written by the cloud ideas session and Vid, and other sessions read it and may add a dated note under an idea, never rewrite or delete one.

## Working in parallel

Vid often has several Claude sessions on Vikix at once. So that none disturbs another, **every session works in its own git worktree by default**, unless Vid says otherwise:

- **Start** by making one beside this repo: `git worktree add ~/src/vikix-TOPIC -b TOPIC` from it, then work only in `~/src/vikix-TOPIC`. A short topic name (`plugins`, `update-core`). If Claude Code's own worktree support is used instead, the same rules hold.
- **This folder is for merging only.** Don't edit here while working on a change; its working tree stays clean, so merges into `main` are always possible.
- **Commit only the files you changed,** by name. Never `git add -A` or `git commit -a`.
- **Finishing:** `git fetch` and rebase the branch onto `main` (resolve conflicts; they show up most in `TODO.md`, `README.md` and `docs/`), run `tests/run.sh --quick` (the full `tests/run.sh` when the change touches `install/`, `packages/`, `features.list` or `dev/`; GitHub runs everything on each push anyway), then in this folder `git merge --ff-only TOPIC`.
- **`VERSION` is bumped at merge time, never earlier,** in the release commit made here after the merge, so two sessions can't both claim the same number. Then tell Vid to run `gup`.
- **Clean up:** `git worktree remove ~/src/vikix-TOPIC` and `git branch -d TOPIC`.
- **Never** force-push, rewrite `main`, or touch another session's worktree or branch. `git worktree list` shows what else is in progress.
- **Cloud sessions** (a clone of their own, pushing straight to GitHub) are already apart: fetch and rebase before every push, never force, and bump `VERSION` only when nobody else's release is in flight (check `git log origin/main` first).

## Checking changes

No build step. The tests are scripts in `tests/`, and `.github/workflows/test.yml` runs the same scripts on GitHub (on each push and weekly):

```sh
tests/run.sh                  # side by side, one per core (VIKIX_TEST_JOBS=1: one at a time), each test's output printed whole when it ends; a few minutes: lint, lisp, battery, memory, gestures, home, services, backup (with restic), image, theme, theme-import, bar, rofi, wallpaper, examples, dev-ai, notes, project, drives, firmware, fingerprint, updates, notifications, idle, lock, lazarus, capture, nightlight, update, windows, ai, ai-local, llm, ai-keys, agents, debug, dictate, voice, lisp-apps, mcp, swank (with Quicklisp), errors (with Quicklisp's StumpWM), bitwarden, plugin, records, obsidian, docs-check, screens, docs, vk, webapp, features, nvim, welcome, menu, pkg, oneline, info, day, viri, main, drawer, rules, keys, registry, why, gather, tray, focus and pixmaps (a real StumpWM on a hidden screen), then times and soak alone (how long the desktop takes, on a hidden screen, against lib/times.limits; a minute of it worked hard, ending as it began), and on Void packages + dry-run
tests/run.sh --quick          # the same without packages, dry-run (Void's mirror), examples and lazarus (minutes each): for changes outside install/, packages/, features.list and dev/
tests/run.sh --all            # plus editors: Emacs's config and Vikix's Neovim config from scratch (minutes, network)
tests/run.sh --changed [REF]  # only the tests for what changed since REF (origin/main), uncommitted included (tests/changed.sh maps files to tests): while working
tests/run.sh lint lisp        # just those
tests/lint.sh                 # bash -n, executable bits, shellcheck -S warning (must stay at zero)
DRY_RUN=1 bash install/<stage>.sh     # one stage, printing instead of changing
```

Because the tests run side by side, a test keeps to its own temporary folder and never takes a fixed real port or display (a made-up `DISPLAY=:7` for stubs is fine; a real Xvfb or listener picks a free one). A new test that can't share goes in `run.sh`'s list to run alone, or is fixed. `lint.sh` uses `shellcheck` from PATH, or `uvx --from shellcheck-py shellcheck` when it isn't installed. A deliberate shellcheck exception gets a `# shellcheck disable=SCxxxx  # why` comment on the line before. A new kind of breakage found by hand should become a check in the matching test. Every test starts with `export VIKIX_SWANK_PORT=9`, so nothing it runs (a theme refresh, a doctor, an update's reload) reaches the live desktop's Swank; lint enforces it (it once sent test passwords to the real Swank and stopped it). Every test also starts with `unset VIKIX_AGENT VIKIX_DIR VIKIX_STATE`, the desktop session's own settings: from an agent's shell they pointed tests at the real `~/vikix` and state and hid the keys, so `ai`, `agents`, `dry-run` (and `home`, `nvim`, `emacs`) failed there; lint enforces that too.

`DRY_RUN=1` works because every system change goes through `run` in `lib/common.sh`, which prints instead of executing. Any new change to the system must go through `run` (or check `DRY_RUN` itself, as `ensure_block` does), or dry runs lie.

Real testing happens in a VM. The dev machine has a libvirt VM `void-vm` (`virsh -c qemu:///system`) with the QEMU guest agent running, so commands can run inside the guest via `virsh qemu-agent-command void-vm '{"execute":"guest-exec",...}'` (then `guest-exec-status` for output). Inside the VM, the checkout is `~/vikix` and is updated with `git pull` or `vikix update`.

## Architecture

**The install is the base, then features** (from 0.47). `install.sh` runs `STAGES` in order: the base lists (every list no feature names), sound, laptop hardware, the login. It writes an empty choices file on a fresh machine (a machine with a migrations record keeps what it had), and `--with NAMES` then runs `vikix add` for them in the same run. The stages up to the login stop at the first failure; those in `GO_ON` (and the features) carry on and are summarised. It asks for sudo once (`sudo_keepalive`) and logs to `~/.local/state/vikix/logs/`. `install-1.sh` is the same as `install.sh`; `install-2.sh` runs `vikix add everything` (both kept for older instructions). A dry run keeps the choices it would write in `VIKIX_DRY_CHOICES`, so its stages see them.

**Stages** (`install/NN-name.sh`) are run with `bash` and each sources `lib/common.sh`. Each must be safe to re-run: check first, then change. `vikix add` re-runs `10-packages` (the new feature's lists), `20-services`, and the editors', languages' and `~/dev` stages when an editor or a language comes. `vikix update` re-runs only `10-packages`, `20-services`, `40-config`, `45-editors`, `65-languages`, `67-dev`, then migrations (`vikix update core` is the first three and the migrations, `system` Void's packages alone, `tools` the last three with llm and the user's pipx/uv/cargo programs); a failed stage is reported at the end and doesn't stop the rest. Shared steps live in `lib/common.sh` (`enable_service`, `ensure_group`, `problem`, …); use them rather than repeating the code.

**Data files, not code, for what gets installed:** `packages/*.list` (one list per concern; `lang-*.list` one per language), `features.list` (what `vikix add`/`remove` offer: each feature's lists, what it needs, and for some a setup command; a list no feature names is the base, installed everywhere; `optional/*.list` only ever come through a feature) and `bundles.list` (essentials, developer, everything), with the user's choices in `~/.config/vikix/features` (`lib/features.sh` reads them; no file means everything, as before 0.46), `services.list` (runit services), `mirrors.list` (mirrors `05-mirror` times), `config/yours.list` (files the snapshot history covers), `themes/*.theme` (colour palettes; `vikix theme` writes them out per program and StumpWM reads them), `dev/<language>/` (what `67-dev` puts in `~/dev`: `README.md` with a `<!-- tools -->` line it fills from `tools.list`, rewritten every update, and `examples/`, copied once). List files allow `#` comments; read them with `read_list`.

**Migrations** (`migrations/<unix-time>.sh`, see `migrations/README.md`). A fresh install gets changes from the stages; machines already installed only get them through a migration, which `vikix update` runs once each, oldest first, and records in `~/.local/state/vikix/migrations/`. `90-finish` marks all existing migrations as applied on a fresh install. So: if a change to a stage must reach existing machines and `vikix update` doesn't already re-run that stage, add a migration. Start it with a `# Why:` comment, and make it safe to run twice.

**File ownership** (the central rule, enforced by `40-config`):
- *Vikix's files* are symlinked into this checkout with `link_managed` (StumpWM `init.lisp` and `vikix/` layer, `.xinitrc`, `vikix.bash`, `bin/*` into `~/.local/bin`, the fontconfig alias, the Claude skill; `45-editors` links Neovim's part, `config/nvim`, to `~/.local/share/vikix/nvim`). Editing them here changes every install on the next `vikix update`.
- *The user's files* are copied once with `copy_user` and never overwritten (`user.lisp`, `rules.lisp`, alacritty/picom/dunst/rofi configs, keyboard file, `.Xresources`; `45-editors` copies Neovim's starter, `config/nvim/starter`, to `~/.config/nvim`, and its tested `lazy-lock.json`, whose Vikix plugins it moves on only while they're still at the versions it left, saved in `~/.local/state/vikix/nvim-lock.json`; `lib/nvim-lock.py` compares and merges). Changing a starter file in `config/` only affects new installs.
- Anything in the way is moved to `<name>.vikix-bak.<time>`, never deleted. Blocks in shared files like `~/.bashrc` go through `ensure_block`.
- *API keys* are neither: `vikix ai key set` keeps them in `~/.config/vikix/secrets/` (700, files 600), `lib/secrets.sh` exports them (the session and every shell), and the snapshot history never records that folder, whatever `yours.list` says (`yours_exclude` in `bin/vikix`, rewritten at every snapshot). Never print a key, and never let `set -x` run where one is read.

**Session and window manager.** Void has no StumpWM package: `30-lisp` installs Quicklisp and `lib/build-stumpwm.lisp` builds `~/.local/bin/stumpwm` with Swank inside. Login on tty1 starts X; `.xinitrc` runs `bin/vikix-session` under `dbus-run-session`, which starts the background programs (pipewire, dunst, picom, guest agents, …) and then StumpWM. `config/stumpwm/init.lisp` loads the layer files in `config/stumpwm/vikix/` in a fixed order (errors → theme → groups → registry → commands → windows → rules → viri → drawer → layouts → overview → day → why → keys → help → webapps → modeline → plugins → swank-guard → swank), then the user's `user.lisp` last. `errors.lisp` comes first and plainly loaded: it loads every other file a form at a time, so a failing form costs only itself, and asks in StumpWM's own menu what to do (skip it, open the file at that line in Emacs, load the user's last snapshot of `user.lisp`); it also catches what StumpWM doesn't (an error in a timer or an X event, which StumpWM answers by restarting) and offers to carry on with a fresh event loop instead. Each error is written to `~/.local/state/vikix/errors/`.

**Rules** (`config/stumpwm/vikix/rules.lisp`; the user's guide is `docs/rules.md`, and `config/stumpwm/rules.lisp` the starter copied once to `~/.stumpwm.d/rules.lisp`, every example a comment that `tests/rules.sh` switches on and loads). `(when-window (:class "Firefox") (workspace 2))`: a rule is a macro call that adds an entry to one table, `*vikix-rules*`, and three named hook functions go through the table; nothing in the layer or a plugin should add a window hook of its own where a rule would do. Verbs live in a table too (`define-rule-verb`), because `float`, `fullscreen` and `title` are taken in StumpWM's package; `when-window` rewrites its body's own forms, so a misspelt verb or matcher fails when the file loads. A rule's run is wrapped: it never lets an error out into StumpWM's event handling, and is switched off at the third failure. A window with a `workspace` rule is put there before it shows, by wrapping `get-window-placement`. A window a rule floats takes the focus when its workspace is in view (`vikix-rule-float-arrives`: StumpWM gives a new window the focus as a tile and only shows a floating one, so a rule `:on :focus` never ran for it and the next tile covered it), and `vikix-rule-float-it` gives the frame in front its window back, which StumpWM's `float-window` takes away; a floating window that arrives on a tiled workspace not in view (a rule, Super+Shift+digit) is shown, with the focus, when that workspace is gone to (`vikix-show-floats` in `windows.lisp`: StumpWM never shows it again). `tests/focus.sh` covers all three. **An agent proposes a rule, it never writes one** (`propose_rule` in `bin/vikix-mcp`, "Rules an agent proposes" in `rules.lisp`): the rule's text is read with `*read-eval*` off and checked by `vikix-rule-proposal-check` (one of the rule forms; its settings plain data; its body only verbs from `*vikix-rule-verbs*` with atoms for values, which must fit the verb's lambda list; no `:where`; then the rule's own macro is expanded for its errors), kept in `*vikix-rule-proposals*` (ten at most), and only Super+m → Rules (`vikix-rules-menu-proposal`) adds it to the user's `rules.lisp` (`vikix-rule-proposal-add`, a snapshot first) or drops it; the menu opens on the rule's own line, so Enter alone adds nothing. There is on purpose no command that accepts one. `tests/propose.sh` drives the real server against a hidden StumpWM. The user's rules are in `~/.stumpwm.d/rules.lisp` (loaded by `init.lisp` just before `user.lisp`) or `user.lisp`. Rules without a window (`at`, `each`, `when-battery-below`, `when-charging`, `when-on-battery`, `at-login`, `when-workspace`) are in the same table and run from one ticker (`vikix-rules-tick`, every 30 seconds, whole numbers only: never a timer a rule) or the focus-group hook. They read the clock and the battery through `*vikix-rules-now*` and `*vikix-rules-battery*`, which the tests replace; what ran is kept by a hash of the rule's key in `~/.local/state/vikix/rules/ran`, and `at-login` notes what ran on the X root window (`_VIKIX_LOGIN_RULES`), which lasts exactly one login. **Don't add a slot to the `vikix-rule` structure:** a changed structure asks questions in every running desktop at the reload that brings it; a rule's settings go in its `match`, and what it remembers in a table by its key. `vikix rules` (`bin/vikix-rules`) only asks the running StumpWM: `vikix-rules-cli` in `rules.lisp` does the work (the list, `off`/`on`, `why`, `test`, `apply`, `verbs`), Super+m → Rules is the same in a menu, `vikix-rules-list` and `vikix-rules-why` answer with data for the MCP server's read-only `rules` tool, and `vikix-rules-problems` is what `vikix doctor` asks. Each window keeps its last few notes of the rules that ran for it (`*vikix-rule-notes*`: key, event, time, failure). Super+Shift+t (`vikix-remember`) writes the rule for the window in front into the user's `~/.stumpwm.d/rules.lisp` (`vikix-remember-write`: a snapshot first, a dated `;; Remembered` comment, `:name "remembered: ..."`, replaced where it stands when remembered again), and `vikix rules forget` takes one out (`vikix-rules-forget`); **the desktop writes to `rules.lisp` only, never to `user.lisp`**, and through a link to the file it names. The layer's own window rules are at the end of `rules.lisp` ("Vikix's own rules": Lazarus's windows floating at their own size, `(float :own t)`; `vikix learn`'s panes), not beside what they are about, because `windows.lisp` and `commands.lisp` load before `rules.lisp` empties the table; a plugin's are in its `plugin.lisp`, and the plugins repo's check refuses an `add-hook` there. `tests/rules.sh` has parts without a screen (`RULES_SKIP_SCREEN=1` runs only those) and a part in a real StumpWM on Xvfb, which also loads the plugins' Lisp at the pin when the plugins repo is at hand.

**The command registry** (`config/stumpwm/vikix/registry.lisp`, loaded before `commands.lisp`). Every command of Vikix's is one form there, `(define-vikix-command NAME "what it does" :run "stumpwm command" | :do FORM, :key, :card, :menu GROUP, :label, :needs, :agent)`, and four things are made from the table, `*vikix-commands*` (plists, in the file's order: never a structure, which a reload would ask about): `*vikix-bindings*` (`keys.lisp`: `(vikix-registry-bindings)`, the commands with a key, in order; the key card and Super+F1 read that list as before), `*vikix-menu*` (`commands.lisp`: `(vikix-registry-menu)`, entries `(LABEL ACTION NEEDS SECTION)`, the menu's sections in `*vikix-menu-groups*`' order, Power last, each section in the file's order, so a command only the menu has is written in `registry.lisp` where its section wants it), what agents may run (`vikix-agent-commands`, `vikix-agent-run`: only `:agent t`, which is for switches and moves put back as easily as done, never a command that prompts, since it would hold StumpWM's main thread, or one that starts a program; `vikix mcp`'s `commands` and `run_command` ask the running desktop, so an agent is never offered a command the desktop doesn't have), and the keys and agent commands in the skill and the README's table of keys (`lib/skill-keys.sh`). **A new command, key or menu entry of Vikix's goes in `registry.lisp`, nowhere else.** The two lists keep their shapes and stay lists: the user's `user.lisp`, plugins (`vikix-plugin-key`, `vikix-plugin-menu`) and web apps still add to them, and a `define-vikix-command` written after `keys.lisp` has bound the keys (`*vikix-registry-live*`: the user's) is bound and put in the menu, before Power, as it is defined. A mistake in a form is an error as the file loads. The file is plain Common Lisp up to its entries' end, so scripts load it without StumpWM: `lib/registry.sh keys|menu|agent` prints it for the tests, and `bin/vikix-webapp` and one migration read `:key "..."` with grep, which is why a form's `:run` and `:key` stay on one line (`tests/lisp.sh` holds the two readings together). `tests/registry.sh` is the real StumpWM's part; `tests/lisp.sh` has the mistakes, the menu's order and what agents are refused.

**Why did that happen?** (`config/stumpwm/vikix/why.lisp`, `Super+?`, `vikix why`, the MCP tool `why`). A ring of the last fifty things the desktop did, in memory only (`*vikix-why-ring*`: plists; the same kind and id again moves to the front, counted, so a rule that runs at every change of focus is one line), each with what made it happen and the file and line that is written at. What notes: `eval-command`, wrapped with `sb-int:encapsulate` (a key's command arrives there with `interactivep` true, after `*key-press-hook*` gave the keys; one from `run-commands` or stumpish is "asked for"; a command a command runs is not noted, `*vikix-why-depth*`); `vikix-run-rule` (rules.lisp calls `vikix-why-rule-ran`, with the window); `vikix-run-menu` (commands.lisp: the entry, and `*vikix-why-cause*` bound so what it runs isn't noted again); `vikix-agent-run` (registry.lisp, the same way). Where a key is written: the registry keeps each command's file and line (`:file`, `:line`, from `*load-truename*` and errors.lisp's `*vikix-load-line*`), and `vikix-bind` notes every other binding in `*vikix-key-sources*`; a key is named the way it was bound (`vikix-why-key-name`: StumpWM prints `C-s-y` for what Vikix writes `s-C-y`). The command shows the list in StumpWM's menu, then what can be done about the one picked (`vikix-why-choices`): edit its line in Emacs when the file is the user's, see it read-only when it is Vikix's (`view-file`), run a switch again, undo a layout change, bring a window a rule moved here, switch the rule off. The last notification comes from dunst's history when the list is shown (`vikix-notifications last`, under `timeout`: never waited on). `tests/why.sh`.

**What is a dialog** (`windows.lisp`: `vikix-dialog-p`, `vikix-born-dialog-p`, `vikix-strip-column-p`). A dialog by what it is (transient, modal, one of `*vikix-dialog-classes*`) is always one. One a rule made (`*vikix-dialog-windows*`, the verb `dialog`) is one only while it floats and is not a column of a strip: a strip's columns are floating windows to StumpWM, Vid's rule calls every floating window that takes the focus a dialog, and `viri-floats-p` leaves a dialog afloat, so with the mark alone every column of a strip stayed floating once its workspace was made tiles and a strip again. The verb itself doesn't mark a column. Anything that asks "does this window float on purpose?" should ask `vikix-dialog-p` or `viri-floats-p`, never the table. `vikix-gather [N]` (Super+m, *Bring every window of another workspace here*; `vikix-gather-windows`) moves a whole workspace's windows here as ordinary windows: it drops a rule's dialog mark, lets a strip's columns be tiled as they arrive (viri.lisp does that), tiles one that floated for another reason, and leaves afloat only a dialog by what it is and a window a rule floats as it opens (`vikix-rules-float-p`); the drawer's windows aren't taken. `tests/gather.sh`.

**The drawer** (`config/stumpwm/vikix/drawer.lisp`, `Super+Ctrl+b`, `vikix-drawer [on|off]`). A few programs (`*vikix-drawer-apps*`: name, shell command, and a rule's matchers for a window another process makes, such as an Emacs frame) floating in a column at the screen's edge over whatever the workspace is, tiles or a strip; away, their windows wait on the hidden workspace `.drawer`. A window opening is the drawer's when a program it started is still waiting for one (the window's `_NET_WM_PID` is that process or a child of it, or the matchers fit). It is taken by a function on `*new-window-hook*` placed just after the rules' own, not by a rule: Vikix's rules run before the user's, and a rule of theirs for the same program (a remembered SpeedCrunch on workspace 1) would take the window out of the drawer again; grid and main and stack come later in the hook and leave a floating window be. Whose a window is, is also written on it (`_VIKIX_DRAWER`), so a restart, which makes every window a tile, finds them again (`vikix-drawer-recover`). Three things StumpWM does that the file works around: a floating window leaving a tiled workspace gives the focus to another floating one there and shows it (an `:around` on `group-delete-window` for `.drawer` alone); a floating window changing workspace is fitted to the screen by `float-window-align`, which fails on one wholly past the edge, so after sliding away the windows are hidden and put back before they move; and a workspace made a strip is a new group, so where the drawer is out is asked of its windows (`vikix-drawer-home`), never kept. `viri-floats-p` and `vikix-raise-dialogs` know the drawer's windows; the bar never lists a hidden workspace. `tests/drawer.sh`.

**The diary** (`bin/vikix-day`, `config/stumpwm/vikix/day.lisp`, idea 4 of `NOVEL.md`). `vikix day` adds a day up from records kept anyway (the projects' logs and commits through `bin/vikix-project`, loaded as a module; `esploro changes`; the snapshot history; the record store; `~/.local/state/vikix/day/docs.log`, which `vikix docs` appends to) and one of its own, `day/screen-YYYY-MM.log`: `vikix-day-tick`, called by the rules' ticker every 30 seconds, never from a focus hook, notes the workspace, its project, the window's class and its program's folder when that changed (never a title), `away` after five idle minutes with how long already, a `beat` every five minutes, and `rule NAME` from `vikix-run-rule`. The Python side treats a gap of more than 400 seconds between lines as the desktop not running, so a suspend or a power cut needs no line of its own. `~/journal/DATE.org` is the user's (700/600), written again each run with what's under `* Notes` kept; `vikix day log` writes a log entry only on a yes in a terminal (`add_entry` and `set_percent` in `vikix-project`). `tests/day.sh` has a made-up home (set `TZ=UTC`, `VIKIX_TODAY`, `VIKIX_NOW`) and a part in a real StumpWM that drives the ticker by hand.

**Plugins** (`bin/vikix-plugin`, `config/stumpwm/vikix/plugins.lisp`) come from their own repo, github.com/vukini/vikix-plugins (`~/src/vikix-plugins` on the dev machine), kept at the commit pinned in `bin/vikix-plugin` in `~/.local/share/vikix/plugins`; moving the pin is a Vikix release, after trying the new commit (`VIKIX_PLUGINS_REPO=~/src/vikix-plugins VIKIX_PLUGINS_COMMIT=$(git -C ~/src/vikix-plugins rev-parse HEAD) vikix plugin sync`). The user's plugins are named in `~/.config/vikix/plugins.list`; their Lisp loads through `vikix-load-file`, so errors ask; they get `vikix-plugin-bar` (the bar's `%P`), `vikix-plugin-key` and `vikix-plugin-menu` (its third argument is the entry's section of Super+m). What plugins find goes in the record store, `vikix records` (`bin/vikix-records`): one SQLite file, `~/.local/share/vikix/records.db` (600, WAL), table `records` (plugin, kind, key, at, title, body, data JSON, link) with an FTS5 index; plugins write with `vikix records add` (JSON on stdin; the same plugin, kind and key updates), and agents read it through `vikix mcp`'s read-only `records_search` and `records_get`.

**Live WM access.** Swank listens on `127.0.0.1:4004`; `vikix eval '(form)'` (`bin/vikix-eval`, Python) runs Lisp in the running StumpWM, in the `STUMPWM` package. It has a password, `~/.slime-secret` (made by `40-config`), sent raw as the first packet, as SLIME does; `swank-guard.lisp` keeps a wrong password from killing Swank's accept thread. The Windows VM is on the NAT bridge virbr0 (0.41.0), so it can't reach 127.0.0.1; before that it was on passt, which maps the guest's gateway to host loopback, which is why Swank got its password. Still, any new local service should authenticate, and never go on passt. `drop_keys` (lib/common.sh) clears API keys from the environment in the installer and `vikix update`.

**Snapshots of the user's files.** `vikix snapshot/changes/history/undo` keep a separate git repo at `~/.local/state/vikix/yours.git` whose work tree is `$HOME`, limited to `config/yours.list`. `vikix agent` snapshots before starting Claude Code.

**The installed agent's skill.** `config/claude/skills/vikix/SKILL.md` is linked to `~/.claude/skills/vikix` on installed machines and guides Claude Code running *on* a Vikix desktop (OpenCode reads it there too). `bin/vikix-agent --write-guide` (40-config, and every `vikix agent`) turns it into `~/.local/share/vikix/AGENTS.md` for the other agents (Codex, Gemini, Aider), so it stays the one source. Update it when commands, keys or file ownership change. Its list of keys is not written by hand: `lib/skill-keys.sh --write` makes it from `registry.lisp` (grouped as the key card), with the commands an agent may run, and from the plugins at the pin, between the `<!-- keys -->`, `<!-- commands -->` and `<!-- plugin-keys -->` markers; run it after changing a command, a key or the plugins' pin. The same run writes `README.md`'s table of keys (between its `<!-- readme-keys -->` markers: a row a key, under the key card's groups), and `--check` fails when either is out of step. `tests/agents.sh` fails when the list is out of date, or when the skill's prose names a key that isn't in it. Super+m shows each entry's key by itself (from `*vikix-bindings*`), so a menu label never names a key. **Super+m is in sections** (`commands.lisp`, `vikix-run-sections`): it opens on a row a section (`vikix-menu-sections`: an entry's fourth element; a plugin's that names none is in Plugins, anything else in Yours; `*vikix-apps-menu*`'s programs are in Apps), each row saying what the section holds (`vikix-menu-hint`, made from the labels up to their colon: `vikix-menu-head`), a section of one entry being that entry; inside a section lines with one head stay together, so a plugin's `Projects: ...` sits under Vikix's; typing at the top shows the entries of every section that match instead (`vikix-menu-row-shown-p`, the menu's filter, which is why `vikix-menu-pick` makes StumpWM's `single-menu` itself rather than call `select-from-menu`). A new entry's label should start with what it is about (`Screens: save this layout`). `vikix-run-menu` is still the plain menu, for the small ones (Power, Dropbox, the user's own). `tests/menu.sh` has the sections without a screen, `tests/registry.sh` the keys in a real StumpWM.

## Conventions

- **Keys keep one rule** (the head of `config/stumpwm/vikix/keys.lisp`; the user's guide: `docs/customize.md`, "The rule for keys"). Super: everyday (the six main apps, the small tools, focus, what is done to the window). Super+Shift: the same key moving the window, or its other way. Super+Alt: open something else, so every other app, every web app (`bin/vikix-webapp` takes no other key) and every plugin key. Super+Ctrl: switch something on the desktop. A new key is written with its command in `registry.lisp` (`:key`), where the rule puts it, with its command in `*vikix-key-everyday*`, `*vikix-key-switches*` or `*vikix-key-movers*` when it is one of those; `tests/lisp.sh` fails on one of Vikix's keys that breaks the rule (`vikix-key-problems`, `help.lisp`), `vikix doctor` names a plugin's, a web app's or the user's. A key taken away from Vikix goes into `*vikix-retired-keys*`, so a running desktop lets it go at the reload. Never write Shift+digit as a key name: it differs by keyboard layout (`vikix-bind-workspace-keys` asks the keyboard). After changing keys, `lib/skill-keys.sh --write` remakes the skill's list.

- Scripts: `set -euo pipefail`, print with `say`/`warn`/`die`, check `pkg_installed` before installing. Watch `pipefail` with assignments from pipelines that may legitimately fail (add `|| true`). Scripts run directly must be executable in git (`100755`).
- Comments explain *why* (Void quirks, ordering reasons), in plain short sentences. README.md is written the same way, with a table row per stage and per package list; keep it in step with the code.
- Releases: bump `VERSION`, commit as `Vikix X.Y.Z: <summary>`, and tag `vX.Y.Z`. Bump the last number (0.71.1 → 0.71.2) for every release, features included; it can go past 9 and on to 100 and beyond. Bump the middle one only when Vid asks, and never go to 1.0 on your own. Tags then sort properly only with `git tag --sort=v:refname`. The user pushes from their own terminal, since their SSH key needs a passphrase that Claude Code's shell can't supply. Tell them the shortcut from their `~/.bashrc`, not raw git: `gup` (push commits and tags, then `vikix update core` into `~/vikix`: Vikix only, in seconds; the usual step after a release. A plain `vikix update` brings Void and the tools, cargo too, and is run now and then), `gtry` (`vikix update core --from ~/src/vikix`: the desktop takes this repo's main straight from here, without GitHub or the passphrase, in a few seconds; for trying a small change, such as a lesson, before pushing; `gup` later pushes the same commits), `gpush` (push this repo and `~/.emacs.d`, tags included, without updating), `gall` (also `~/.dotfiles`); `gpl` pulls. On the dev machine these go through the `repos` plugin, which knows every project: `repos push` (pinned projects, Esploro and the plugins, before Vikix, and never a pin GitHub hasn't got), `repos pull`, `repos ship` (what `gup` runs: push, then `vikix update core`), `repos update` (the whole system); `repos` alone says what each needs, including commits past Vikix's pin. To see whether GitHub has anything new without the key, fetch over HTTPS: `git fetch https://github.com/vukini/vikix.git main:refs/remotes/origin/main`.
- Void specifics: runit services are enabled by symlinking `/etc/sv/<name>` into `/var/service/`; xbps repository overrides go in `/etc/xbps.d/` (same filename as in `/usr/share/xbps.d/`); `xbps` must be updated before other installs on a fresh system.
