# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Vikix is an opinionated desktop layer for **glibc Void Linux** built around **StumpWM**: Void, supercharged. It was inspired by Omarchy but is its own thing: credit Omarchy as the inspiration, but don't call Vikix "Omarchy for Void". It is not a distribution; it's a set of bash install stages run on top of a plain Void install, plus the config it puts in place and a `vikix` command that keeps it current. Repo: github.com/vukini/vikix (MIT).

This repo lives in `~/src/vikix` on the dev machine (until 2026-10-01 it was inside the Obsidian vault, `~/General/Living-in-Life/vikix`). The `vikix-*.zip` files are old releases and are gitignored.

**Edit in this repo (in a worktree of it: see Working in parallel), never in `~/vikix`.** This repo is where Vikix is developed. `~/vikix` on the dev machine is the installed checkout: it only pulls from GitHub, to see Vikix the way a user does. Don't edit, commit or stash there; `vikix update` sets edits aside and stops on commits. To try a change on the desktop before any release, commit it at your desk and run `vikix try` there (see Working in parallel); once released, Vid's `gup` pushes and updates.

`site/` is the website, vikix.dev: static pages (`index.html`, `gallery.html`) sharing `site.css`, screenshots in `site/shots/` (each scene as `NAME-vikix-dark.webp` and `NAME-vikix-light.webp`, 960px copies in `small/`), and `install`, the one-line install (`curl -fsSL https://vikix.dev/install | bash`: checks, clones, runs install.sh; one function called on the last line, so a cut-off download runs nothing), no build of its own, published by `.github/workflows/pages.yml` on each push that touches `site/`, `VERSION` or the guides (the workflow writes `VERSION` into the page, and builds `docs/` into `site/guide/`, vikix.dev/guide/, with `lib/build-guide.sh --site`; that folder is gitignored, never committed). When a release adds something a visitor would care about (a key, a feature card), update the page in the same commit.

`installer/` is Vikix's installer stick (TODO 20; the user's guide is `docs/install-stick.md`). `build-image.sh` (root, xbps on PATH) makes the ISO with void-mklive at a pinned commit: Void's live system with today's kernel and firmware, a clone of this repo in `/usr/share/vikix`, and `live/` laid over it, whose `profile.d` script starts `vikix-installer` on tty1. `vikix-installer` (dialog; `--answers FILE`, `--dry-run`) erases one whole disk, 1 GiB EFI as `/boot` then optional LUKS2 with ext4, installs Void from the network with NetworkManager on and the stick's Wi-Fi copied, copies Vikix to `~/vikix`, and leaves a marker plus a `vikix firstboot` block in `~/.bash_profile`; `firstboot` runs `install.sh` at the first tty1 login and removes both on success. It is not a stage: nothing of `install/` runs on the stick. `tests/installer.sh` checks the dry run and `firstboot`; `installer/qemu-test.py ISO DIR` is the end-to-end run in QEMU (UEFI, encrypted install, first start), by hand.

`docs/` holds the user's guides (the map of files, how it fits together, customizing, fixing). They name real paths, keys, variables and commands: when a change moves or renames one, update the guide in the same commit. `40-config` also makes them an Info manual, `~/.local/share/info/vikix.info` (`info vikix`, Emacs `C-h i`), through `lib/md2texi.py`, which knows only the Markdown the guides use; It also makes them web pages, `~/.local/share/vikix/guide/` (`lib/build-guide.sh`: `makeinfo --html`, styled by `docs/guide.css`), and the same pages are the site's guide, vikix.dev/guide/, so a change to `docs/` reaches the site on its next push. Diagrams are `![what it shows](diagrams/NAME.svg)` on a line of their own, three files in `docs/diagrams/`: `NAME.mmd` (Mermaid source), `NAME.svg` (committed, drawn by `docs/diagrams/render.sh` with the system Chromium, ending with the source's SHA-1) and `NAME.txt` (the plain-text version Info shows). `tests/info.sh` fails on a broken link, a page missing from `docs/README.md`'s table, a makeinfo warning, a diagram missing a file, or an SVG not drawn from its current source. The `explainer` agent (`.claude/agents/explainer.md`) writes and keeps the guides and diagrams. `.claude/docs-check` (cron, Mondays at 10 on the dev machine) looks for guides gone stale: the plugins guide against the plugins repo (a section, every key, every setting), and commits since the last review that changed `bin/`, `config/`, `install/`, `packages/` or a plugin without the guides. It asks Vid in a dialog first; only on his yes does Claude Code open with what it found. Update the guides then with the explainer, show Vid the changes before committing, and finish with `.claude/docs-check --reviewed`.

**Every `bin/vikix*` starts with a header in one shape,** and three things are made from it: `-h` prints it (`sed -n '2,/^$/p'`, or the docstring), `vikix help` prints `bin/vikix`'s, and `lib/man.py` turns it into the command's man page (`40-config` writes them to `~/.local/share/man/man1/`; `MANPATH` is set by `vikix-session` and `vikix.bash`, since Void's `man`, mandoc, doesn't look beside `~/.local/bin`). The shape: `# vikix-NAME — one line`, then indented usage lines, `vikix NAME sub ARGS`, two spaces or more, `what it does` (further lines of it indented deeper), then prose; an indented block that doesn't start with the command is shown as it is. So a new command or option is documented by editing the header, nowhere else. `tests/lint.sh` fails a header out of shape (`python3 lib/man.py --check` says why); `python3 lib/man.py --page bin/vikix-NAME | mandoc | less` shows a page while writing. Two more things come from the same headers. `docs/commands.md` is them as a guide page, committed: **after changing any header, run `python3 lib/man.py --guide > docs/commands.md`**, or `tests/man.sh` fails; never edit that file by hand. And the commands of the plugins in the user's list get pages as well (`man inbox`): `lib/man.py` reads `~/.config/vikix/plugins.list`, `vikix plugin add`, `remove` and a moved pin run it again, a plugin's header out of shape only costs that page, and the plugins repo's `tests/check.sh` checks the shape (`python3 lib/man.py --check PLUGIN/bin`). It never writes over a page it didn't make.

`TODO.md` lists planned features and cleanups, numbered. Read it when asked what's next, and remove an item in the commit that ships it; a number is never used twice (the commits, the memories and this file cite them), so a new item takes the number after the highest ever given, not the highest still in the list. `IDEAS.md` holds ideas not yet decided on; one moves to `TODO.md` when it is picked up. `bugs.md` lists small known problems not yet fixed (what happens, what's known, the next step); a fix removes its entry. `NOVEL.md` holds the ideas no other desktop does, kept apart so they aren't lost among the small ones; it is written by the cloud ideas session and Vid, and other sessions read it and may add a dated note under an idea, never rewrite or delete one. **The longer plans are in `plans/`**, one line each in `plans/README.md`: the worked-out designs (`DESIGN-*.md`, each dated, what ships deleted from it, what changes dated; one moves into `TODO.md` when work starts, as Esploro's did), what is left for the editors (`TODO-editors.md`) and for Windows programs in their own windows (`TODO-Windows.md`), the AI desktop at work (`ai-desktop.md`), the courses of `vikix learn` (`TUTORIALS.md`) and programs worth trying (`APP-IDEAS.md`). A new design goes in that folder with a line in its index, and nowhere in this file.

## Diagnostic processes and completion checks

Before saying work is finished:

- **Bound every one-off diagnostic.** Use a timeout with a termination deadline (for example, `timeout --kill-after=5s 30s COMMAND`), or an equivalent subprocess timeout with cleanup. A tool returning a background session ID means the command is still running, not that it completed. Collect its exit status. Stop a check that repeats the same output without progress and fix it before retrying. In Emacs scan loops, use `save-excursion` around helpers that can move point, and verify each iteration advances.
- **Own the processes you start.** Record each background job's tool session ID or PID and its purpose. Install cleanup before starting test daemons, servers or hidden displays, including error, timeout and interruption paths. Stop only your own processes, wait for their exit, and verify they are gone; never use a broad process-name kill that could reach the user's Emacs or another agent's jobs.
- **Test the real entry point and starting state.** For launch changes, exercise the public launcher in an isolated environment, with stand-in backends as needed. Include the relevant initial states: for Office, an Emacs daemon with no graphical frames as well as an existing graphical Emacs, unavailable server/display, and safe argument handling. A direct call to the UI function alone does not validate its launcher. Keep these tests under `tests/run.sh`, away from live sessions and private documents.
- **Audit cleanup before handing back.** Review every background job started during the task, including exploratory commands outside the test suite. Confirm each has exited and collect its result. If a sandbox hides a known process, obtain the necessary permission to verify it; an empty sandbox process list is not evidence of cleanup. Leave a process running only when the user wants it, and state what remains running and why.
- **Report the evidence precisely.** Distinguish unit tests, isolated end-to-end checks, visual inspection on a test display, and validation on the user's desktop. Say what could not be tested. Do not call a passing test proof that the installed desktop works, or say cleanup is complete without checking.

## Working in parallel

Vid often has several Claude sessions on Vikix at once. So that none disturbs another, **every session works in its own git worktree by default**, unless Vid says otherwise:

- **Start by taking a desk:** `vikix agents sit vikix TOPIC` from your shell makes the worktree `~/src/vikix-TOPIC` on the branch `TOPIC` (or takes the one that is there) and seats you at it; then work only in `~/src/vikix-TOPIC`. A short topic name (`plugins`, `update-core`). A desk Vid started you at (`vikix agents desk`) is yours already. If Claude Code's own worktree support is used instead, the same rules hold: run `vikix agents sit` (no words) from inside it, since your process still sits in its first folder and the hook knows only the seat. **No desk, no work:** the house rules (`vikix agents touch`, the office's hook) refuse an Edit, a Write or a Bash command that would write into this repository, or any project's, from a session that isn't at a desk, with how to sit down; reading is free.
- **This folder is for merging only.** Don't edit here while working on a change; its working tree stays clean, so merges into `main` are always possible. The hook refuses a change here from any desk.
- **Commit only the files you changed,** by name. Never `git add -A` or `git commit -a`.
- **Trying it on the desktop before the release: `vikix try`** (`cmd_try` in `bin/vikix`; `vikix try help`), from the desk or as `vikix try TOPIC`: `~/vikix` fetches the desk's last commit and checks it out detached, notes it in `$VIKIX_STATE/try` (folder, commit, branch, when), and runs `vikix update --pulled core` from the desk's copy of the script (the stages, migrations, plugin sync, StumpWM reload), ending with what the desktop runs. It takes commits only (uncommitted files at the desk are refused) and one desk at a time (the next try replaces it). `try_back`, called by every `vikix update core` before its pull and by `vikix try off`, puts `~/vikix` back on main, so a try is never kept over an update and `gup` works unchanged. `vikix try status` and the first line of `vikix agents` say what runs. `vikix agents desks` lists the desks for scripts (folder, branch, own folder). Vid's `gtry` still takes this repository's main. `tests/try.sh`, in a made-up checkout with stubbed stages.
- **Finishing: `.claude/release TOPIC "what it brings, in a line"`**, from anywhere, once everything is committed in the worktree. It waits its turn (one release at a time, a lock in the repository; `.claude/release --queue`, Vid's `gq`, shows who is testing and who waits, from the note each release keeps of itself in `.git/vikix-release-queue/`; the Office shows the same notes as its Releases box, `release_queue` in `lib/office.py`, and marks the desk under release), puts the branch on top of `main` as it is now (stopping, with nothing changed, when both changed the same lines: then `git rebase main` in the worktree, settle them, and release again), runs the tests the changes reach (`--tests quick` or `full` for more: `full` when the change touches `install/`, `packages/`, `features.list` or `dev/`; `--tests none` when you ran them on that very commit), fast-forwards `main`, bumps `VERSION`, commits `Vikix X.Y.Z: ...` (`--co-author "Name <mail>"` adds the line), tags it, and removes the worktree and the branch. `--plain` for a change with no release (`TODO.md`, a plan). Then tell Vid to run `gup`, and say that your desk (the worktree and the branch) is gone, so he isn't left looking for it; the same when he closes your desk by hand. Don't do these steps by hand: a merge that was refused, followed by a bump and a tag all the same, has put an empty release on `main` twice.
- **`VERSION` is bumped at merge time, never earlier,** by that script, so two sessions can't both claim the same number.
- **Never** force-push, rewrite `main`, or touch another session's worktree or branch. `git worktree list` shows what else is in progress.
- **Cloud sessions** (a clone of their own, pushing straight to GitHub) never release: no `VERSION` bump, no tag. They push their branch, say so, and a session on the dev machine releases it from a desk. On 2026-10-06 a cloud session's releases pushed to GitHub took the numbers 0.71.212 and 0.71.213, the dev machine took the same ones, and `gup` was refused; since then `.claude/release` looks at origin's main first (over HTTPS, no key) and stops when this main is behind it (*Vid: gpl, then release again*).

## Checking changes

**Tests queue across sessions.** Every `tests/run.sh` on the machine draws from one set of slots, as many as there are cores, so several sessions' runs don't add up (a load of 70 to 100 once made tests fail for slowness alone); a test in the `alone` list (`times`, `soak`, `rescue`) runs while no other test runs anywhere. So run tests through the runner, a single one too (`tests/run.sh rules`, not `tests/rules.sh`), and don't start a second run to "save time": it only waits.

No build step. The tests are scripts in `tests/`, and `.github/workflows/test.yml` runs the same scripts on GitHub (on each push and weekly):

```sh
tests/run.sh                  # side by side, one per core (VIKIX_TEST_JOBS=1: one at a time), each test's output printed whole when it ends; a few minutes: lint, lisp, battery, memory, gestures, home, services, backup (with restic), image, theme, theme-import, bar, rofi, wallpaper, examples, dev-ai, notes, project, drives, firmware, fingerprint, updates, notifications, idle, lock, lazarus, capture, nightlight, update, windows, ai, ai-local, llm, ai-keys, agents, debug, dictate, voice, lisp-apps, mcp, swank (with Quicklisp), errors (with Quicklisp's StumpWM), bitwarden, plugin, records, obsidian, docs-check, screens, docs, vk, webapp, features, nvim, welcome, menu, pkg, oneline, info, day, viri, main, drawer, rules, keys, registry, why, what, gather, workspaces, office, tray, focus and pixmaps (a real StumpWM on a hidden screen), then times and soak alone (how long the desktop takes, on a hidden screen, against lib/times.limits; a minute of it worked hard, ending as it began), and on Void packages + dry-run
tests/run.sh --quick          # the same without packages, dry-run (Void's mirror), examples and lazarus (minutes each): for changes outside install/, packages/, features.list and dev/
tests/run.sh --all            # plus editors: Emacs's config and Vikix's Neovim config from scratch (minutes, network)
tests/run.sh --changed [REF]  # only the tests for what changed since REF (origin/main), uncommitted included (tests/changed.sh maps files to tests; a change to bin/vikix by the part of the file it touches, so one command's arm costs that command's test, not the set): while working
tests/run.sh lint lisp        # just those
tests/lint.sh                 # bash -n, executable bits, shellcheck -S warning (must stay at zero)
DRY_RUN=1 bash install/<stage>.sh     # one stage, printing instead of changing
```

Because the tests run side by side, a test keeps to its own temporary folder and never takes a fixed real port or display (a made-up `DISPLAY=:7` for stubs is fine; a real Xvfb or listener picks a free one). A new test that can't share goes in `run.sh`'s list to run alone, or is fixed. `lint.sh` uses `shellcheck` from PATH, or `uvx --from shellcheck-py shellcheck` when it isn't installed. A deliberate shellcheck exception gets a `# shellcheck disable=SCxxxx  # why` comment on the line before. A new kind of breakage found by hand should become a check in the matching test. Every test starts with `export VIKIX_SWANK_PORT=9`, so nothing it runs (a theme refresh, a doctor, an update's reload) reaches the live desktop's Swank; lint enforces it (it once sent test passwords to the real Swank and stopped it). Every test also starts with `unset VIKIX_AGENT VIKIX_DIR VIKIX_STATE`, the desktop session's own settings: from an agent's shell they pointed tests at the real `~/vikix` and state and hid the keys, so `ai`, `agents`, `dry-run` (and `home`, `nvim`, `emacs`) failed there; lint enforces that too.

`DRY_RUN=1` works because every system change goes through `run` in `lib/common.sh`, which prints instead of executing. Any new change to the system must go through `run` (or check `DRY_RUN` itself, as `ensure_block` does), or dry runs lie.

Real testing happens in a VM. The dev machine has a libvirt VM `void-vm` (`virsh -c qemu:///system`) with the QEMU guest agent running, so commands can run inside the guest via `virsh qemu-agent-command void-vm '{"execute":"guest-exec",...}'` (then `guest-exec-status` for output). Inside the VM, the checkout is `~/vikix` and is updated with `git pull` or `vikix update`.

## Architecture

**The install is the base, then features** (from 0.47). `install.sh` runs `STAGES` in order: the base lists (every list no feature names), sound, laptop hardware, the login. It writes an empty choices file on a fresh machine (a machine with a migrations record keeps what it had), and `--with NAMES` then runs `vikix add` for them in the same run. The stages up to the login stop at the first failure; those in `GO_ON` (and the features) carry on and are summarised. It asks for sudo once (`sudo_keepalive`) and logs to `~/.local/state/vikix/logs/`. `install-1.sh` is the same as `install.sh`; `install-2.sh` runs `vikix add everything` (both kept for older instructions). A dry run keeps the choices it would write in `VIKIX_DRY_CHOICES`, so its stages see them.

**Stages** (`install/NN-name.sh`) are run with `bash` and each sources `lib/common.sh`. Each must be safe to re-run: check first, then change. `vikix add` re-runs `10-packages` (the new feature's lists), `20-services`, and the editors', languages' and `~/dev` stages when an editor or a language comes. `vikix update` re-runs only `10-packages`, `20-services`, `40-config`, `45-editors`, `65-languages`, `67-dev`, then migrations (`vikix update core` is the first three and the migrations, `system` Void's packages alone, `tools` the last three with llm and the user's pipx/uv/cargo programs); a failed stage is reported at the end and doesn't stop the rest. Shared steps live in `lib/common.sh` (`enable_service`, `ensure_group`, `problem`, …); use them rather than repeating the code.

**Data files, not code, for what gets installed:** `packages/*.list` (one list per concern; `lang-*.list` one per language), `features.list` (what `vikix add`/`remove` offer: each feature's lists, what it needs, and for some a setup command; a list no feature names is the base, installed everywhere; `optional/*.list` only ever come through a feature) and `bundles.list` (essentials, developer, everything), with the user's choices in `~/.config/vikix/features` (`lib/features.sh` reads them; no file means everything, as before 0.46), `services.list` (runit services), `mirrors.list` (mirrors `05-mirror` times), `config/yours.list` (files the snapshot history covers), `themes/*.theme` (colour palettes; `vikix theme` writes them out per program and StumpWM reads them), `dev/<language>/` (what `67-dev` puts in `~/dev`: `README.md` with a `<!-- tools -->` line it fills from `tools.list`, rewritten every update, and `examples/`, copied once). List files allow `#` comments; read them with `read_list`.

**Migrations** (`migrations/<unix-time>.sh`, see `migrations/README.md`). A fresh install gets changes from the stages; machines already installed only get them through a migration, which `vikix update` runs once each, oldest first, and records in `~/.local/state/vikix/migrations/`. `90-finish` marks all existing migrations as applied on a fresh install. So: if a change to a stage must reach existing machines and `vikix update` doesn't already re-run that stage, add a migration. Start it with a `# Why:` comment, and make it safe to run twice.

**File ownership** (the central rule, enforced by `40-config`):
- *Vikix's files* are symlinked into this checkout with `link_managed` (StumpWM `init.lisp` and `vikix/` layer, `.xinitrc`, `vikix.bash`, `bin/*` into `~/.local/bin`, the fontconfig alias, the Claude skill; `45-editors` links Neovim's part, `config/nvim`, to `~/.local/share/vikix/nvim`). Editing them here changes every install on the next `vikix update`.
- *The user's files* are copied once with `copy_user` and never overwritten (`user.lisp`, `rules.lisp`, alacritty/picom/dunst/rofi configs, keyboard file, `.Xresources`; `45-editors` copies Neovim's starter, `config/nvim/starter`, to `~/.config/nvim`, and its tested `lazy-lock.json`, whose Vikix plugins it moves on only while they're still at the versions it left, saved in `~/.local/state/vikix/nvim-lock.json`; `lib/nvim-lock.py` compares and merges). Changing a starter file in `config/` only affects new installs.
- Anything in the way is moved to `<name>.vikix-bak.<time>`, never deleted. Blocks in shared files like `~/.bashrc` go through `ensure_block`.
- *API keys* are neither: `vikix ai key set` keeps them in `~/.config/vikix/secrets/` (700, files 600), `lib/secrets.sh` exports them (the session and every shell), and the snapshot history never records that folder, whatever `yours.list` says (`yours_exclude` in `bin/vikix`, rewritten at every snapshot). Never print a key, and never let `set -x` run where one is read.

**Session and window manager.** Void has no StumpWM package: `30-lisp` installs Quicklisp and `lib/build-stumpwm.lisp` builds `~/.local/bin/stumpwm` with Swank inside. Login on tty1 starts X; `.xinitrc` runs `bin/vikix-session` under `dbus-run-session`, which starts the background programs (pipewire, dunst, picom, guest agents, …) and then StumpWM. `config/stumpwm/init.lisp` loads the layer files in `config/stumpwm/vikix/` in a fixed order (errors → theme → groups → registry → commands → windows → rules → viri → drawer → layouts → overview → day → why → what → agents → keys → help → webapps → modeline → plugins → rescue → door → swank-guard → swank → socket), then the user's `user.lisp` last. `errors.lisp` comes first and plainly loaded: it loads every other file a form at a time, so a failing form costs only itself, and asks in StumpWM's own menu what to do (skip it, open the file at that line in Emacs, load the user's last snapshot of `user.lisp`); it also catches what StumpWM doesn't (an error in a timer or an X event, which StumpWM answers by restarting) and offers to carry on with a fresh event loop instead. Each error is written to `~/.local/state/vikix/errors/`.

**Rules** (`config/stumpwm/vikix/rules.lisp`; the user's guide is `docs/rules.md`, and `config/stumpwm/rules.lisp` the starter copied once to `~/.stumpwm.d/rules.lisp`, every example a comment that `tests/rules.sh` switches on and loads). `(when-window (:class "Firefox") (workspace 2))`: a rule is a macro call that adds an entry to one table, `*vikix-rules*`, and three named hook functions go through the table; nothing in the layer or a plugin should add a window hook of its own where a rule would do. Verbs live in a table too (`define-rule-verb`), because `float`, `fullscreen` and `title` are taken in StumpWM's package; `when-window` rewrites its body's own forms, so a misspelt verb or matcher fails when the file loads. A rule's run is wrapped: it never lets an error out into StumpWM's event handling, and is switched off at the third failure. A window with a `workspace` rule is put there before it shows, by wrapping `get-window-placement`. A window a rule floats takes the focus when its workspace is in view (`vikix-rule-float-arrives`: StumpWM gives a new window the focus as a tile and only shows a floating one, so a rule `:on :focus` never ran for it and the next tile covered it), and `vikix-rule-float-it` gives the frame in front its window back, which StumpWM's `float-window` takes away; a floating window that arrives on a tiled workspace not in view (a rule, Super+Shift+digit) is shown, with the focus, when that workspace is gone to (`vikix-show-floats` in `windows.lisp`: StumpWM never shows it again). `tests/focus.sh` covers all three. **An agent proposes a rule, it never writes one** (`propose_rule` in `bin/vikix-mcp`, "Rules an agent proposes" in `rules.lisp`): the rule's text is read with `*read-eval*` off and checked by `vikix-rule-proposal-check` (one of the rule forms; its settings plain data; its body only verbs from `*vikix-rule-verbs*` with atoms for values, which must fit the verb's lambda list; no `:where`; then the rule's own macro is expanded for its errors), kept in `*vikix-rule-proposals*` (ten at most), and only Super+m → Rules (`vikix-rules-menu-proposal`) adds it to the user's `rules.lisp` (`vikix-rule-proposal-add`, a snapshot first) or drops it; the menu opens on the rule's own line, so Enter alone adds nothing. There is on purpose no command that accepts one. `tests/propose.sh` drives the real server against a hidden StumpWM. The user's rules are in `~/.stumpwm.d/rules.lisp` (loaded by `init.lisp` just before `user.lisp`) or `user.lisp`. Rules without a window (`at`, `each`, `when-battery-below`, `when-charging`, `when-on-battery`, `at-login`, `when-workspace`) are in the same table and run from one ticker (`vikix-rules-tick`, every 30 seconds, whole numbers only: never a timer a rule) or the focus-group hook. Rules for things that come and go (`when-screen`, `when-network`, `when-drive`, each with a `-gone`, and `when-idle`) are in the table too and run from a second whole-number timer, the look (`vikix-rules-look`, every 5 seconds, doing nothing while no rule asks). What is there comes from `*vikix-rules-things*` (StumpWM's heads; the bar's `*vikix-net*`, which the bar's thread reads, so no program runs in the main thread; `/proc/mounts` under `/run/media/USER`, never a `stat` of a drive), and what each rule saw last is noted by its hash on the root window (`_VIKIX_RULES_SEEN`, UTF-8), which is what makes a login's things arrive and a reload's not; a new source of names is a case in `vikix-rules-read-things` and a line in `*vikix-rule-things*`, and must be able to answer `:unknown`. `tests/events.sh`. An agent's Lisp is checked before it runs: `vikix-eval-forms` (swank.lisp) reads every form with `*read-eval*` off, and with `:door t` walks each (`vikix-door-check`: a form is fine when every function it calls is in `*vikix-door-allowed*`, the registry's `:agent t` commands or `~/.config/vikix/door`; a local variable may be set, a global or a place may not; `funcall`/`apply` only of a name written there; a quoted name counts as a call) before any runs; the first problem holds the whole text (`vikix-door-hold`: `*vikix-door-held*`, ten at most, a notification, and a report in `errors/` for the `:refused` kinds of `*vikix-door-refused*`: shell, file, eval, system; `*vikix-door-asks*` is held without a report: defining, waiting), `:HELD` goes back and `vikix eval` exits 3. **Whose a form is, is decided by `bin/vikix-eval`** (`whose`): going up `/proc` from its parent, the first thing met decides: an agent of `AGENTS` (the same list as `bin/vikix-agents`' `PROGRAMS`, held together by `tests/door.sh`) makes it the agent's, a script of Vikix's (`vikix`, `vikix-*`) makes it Vikix's own, so `vikix theme` run by an agent passes and the MCP server's own forms pass while its `eval` tool asks with `--door`; the door stands only at the desktop's port 4004 (`--door` forces it elsewhere, for the tests), `--whose` prints the decision, and a desktop without `vikix-door-check` refuses an agent's form rather than run it unchecked. A new read or act an agent should have goes in `*vikix-door-allowed*` (names, upcased; the file is plain Common Lisp up to "The desktop", and the test loads it in bare SBCL); nothing that prompts, starts a program or writes. `tests/door.sh`.

**What is a dialog** (`windows.lisp`: `vikix-dialog-p`, `vikix-born-dialog-p`, `vikix-strip-column-p`). A dialog by what it is (transient, modal, one of `*vikix-dialog-classes*`) is always one. One a rule made (`*vikix-dialog-windows*`, the verb `dialog`) is one only while it floats and is not a column of a strip: a strip's columns are floating windows to StumpWM, Vid's rule calls every floating window that takes the focus a dialog, and `viri-floats-p` leaves a dialog afloat, so with the mark alone every column of a strip stayed floating once its workspace was made tiles and a strip again. The verb itself doesn't mark a column. Anything that asks "does this window float on purpose?" should ask `vikix-dialog-p` or `viri-floats-p`, never the table. `vikix-gather [N]` (Super+m, *Bring every window of another workspace here*; `vikix-gather-windows`) moves a whole workspace's windows here as ordinary windows: it drops a rule's dialog mark, lets a strip's columns be tiled as they arrive (viri.lisp does that), tiles one that floated for another reason, and leaves afloat only a dialog by what it is and a window a rule floats as it opens (`vikix-rules-float-p`); the drawer's windows aren't taken. `tests/gather.sh`.

**The drawer** (`config/stumpwm/vikix/drawer.lisp`, `Super+Ctrl+b`, `vikix-drawer [on|off]`). A few programs (`*vikix-drawer-apps*`: name, shell command, and a rule's matchers for a window another process makes, such as an Emacs frame) floating in a column at the screen's edge over whatever the workspace is, tiles or a strip; away, their windows wait on the hidden workspace `.drawer`. A window opening is the drawer's when a program it started is still waiting for one (the window's `_NET_WM_PID` is that process or a child of it, or the matchers fit). It is taken by a function on `*new-window-hook*` placed just after the rules' own, not by a rule: Vikix's rules run before the user's, and a rule of theirs for the same program (a remembered SpeedCrunch on workspace 1) would take the window out of the drawer again; grid and main and stack come later in the hook and leave a floating window be. Whose a window is, is also written on it (`_VIKIX_DRAWER`), so a restart, which makes every window a tile, finds them again (`vikix-drawer-recover`). Three things StumpWM does that the file works around: a floating window leaving a tiled workspace gives the focus to another floating one there and shows it (an `:around` on `group-delete-window` for `.drawer` alone); a floating window changing workspace is fitted to the screen by `float-window-align`, which fails on one wholly past the edge, so after sliding away the windows are hidden and put back before they move; and a workspace made a strip is a new group, so where the drawer is out is asked of its windows (`vikix-drawer-home`), never kept. `viri-floats-p` and `vikix-raise-dialogs` know the drawer's windows; the bar never lists a hidden workspace. `tests/drawer.sh`.

**The diary** (`bin/vikix-day`, `config/stumpwm/vikix/day.lisp`, idea 4 of `NOVEL.md`). `vikix day` adds a day up from records kept anyway (the projects' logs and commits through `bin/vikix-project`, loaded as a module; `esploro changes`; the snapshot history; the record store; `~/.local/state/vikix/day/docs.log`, which `vikix docs` appends to) and one of its own, `day/screen-YYYY-MM.log`: `vikix-day-tick`, called by the rules' ticker every 30 seconds, never from a focus hook, notes the workspace, its project, the window's class and its program's folder when that changed (never a title), `away` after five idle minutes with how long already, a `beat` every five minutes, and `rule NAME` from `vikix-run-rule`. The Python side treats a gap of more than 400 seconds between lines as the desktop not running, so a suspend or a power cut needs no line of its own. `~/journal/DATE.org` is the user's (700/600), written again each run with what's under `* Notes` kept; `vikix day log` writes a log entry only on a yes in a terminal (`add_entry` and `set_percent` in `vikix-project`). `tests/day.sh` has a made-up home (set `TZ=UTC`, `VIKIX_TODAY`, `VIKIX_NOW`) and a part in a real StumpWM that drives the ticker by hand.

**Loading, and threads.** `init.lisp` loads each layer file from a compiled copy (`~/.cache/vikix/fasl/NAME-KEY.fasl`; `VIKIX_FASL_DIR` for the tests' shared one) when there is one, else from its text a form at a time (`vikix-load-forms`), queueing it for a compiler thread that makes the copy after the load. The key chains the texts of all files loaded so far, so a change invalidates everything after it. A layer file must therefore mean the same compiled as read: don't depend on the order in which one file's own top-level forms are evaluated beyond what `compile-file` gives (a macro used in the file that defines its helper functions is fine: the copy is compiled after the text was loaded). Ask which file is loading with `(or (and (boundp '*vikix-loading-file*) (symbol-value '*vikix-loading-file*)) *load-truename*)`, never `*load-truename*` alone (it is the copy's). `errors.lisp` and `registry.lisp` stay on text (`*vikix-source-only*`). StumpWM's main thread should never wait on a program: the bar's refreshers (`*vikix-bar-refreshers*`, `modeline.lisp`) run in the `vikix-bar` thread, so a refresher only runs its program, sets its variable and calls `vikix-bar-redraw` (never `update-all-mode-lines`, `message` or anything that draws). The threads there are: `vikix-bar`, `vikix-watch` and `vikix-rescue-key` (rescue), `vikix-compiler` (while copies are made), `vikix-socket` and `vikix-socket-client` (the socket). `tests/reload.sh` covers the loader and the bar's thread. **The tray** (`vikix tray on`: stumptray, started from `modeline.lisp`) is a window inside the bar's, and StumpWM makes the bar anew when it is hidden and shown or a screen changes: `vikix-tray-bar-gone` and `vikix-tray-bar-new` (the mode line's two hooks) take it down and put it up with the bar, and the bar's round (`vikix-tray-refresh`, which asks the main thread for `vikix-tray-tend`) finds one left behind (`vikix-tray-stale-p`: Lisp only), forgets it without a request to the X server, makes a new one and restarts its applets, whose icons went with the old window. The bar's network and Bluetooth fields step aside only for an icon that is in the tray (`*vikix-tray-icons*`, by window class), never because the tray is merely on. `tests/tray.sh` stands in for `pgrep`, `pkill` and the two applets, since the real ones see the whole machine.

**Resume** (`config/stumpwm/vikix/resume.lisp`, `bin/vikix-resume`). The session back after a restart is `layouts.lisp` applied to every workspace: saved every five minutes and at `*quit-hook*` into `~/.local/state/vikix/resume/` (with `*vikix-layouts-dir*` bound there), put back one workspace at a time by a one-second timer (a layout is restored on the workspace in view, where its programs' windows open). A new login is told by a note on X's root window (`_VIKIX_RESUME`), as `at-login` rules are; nothing is saved before that login's question is settled, or an empty desktop would replace what was saved. `tests/resume.sh` makes several logins, each on an X server of its own.

**What gets used** (`config/stumpwm/vikix/used.lisp`, `bin/vikix-used`). `vikix-why-note` (why.lisp) is the one place every key, menu entry, rule, typed command and agent's command passes; it hands each to `vikix-used-note`, which counts it (the palette's picks come from `vikix-palette-run`). The table is `*vikix-used*`, "KIND<tab>WHAT" to (count first last), read once from `~/.local/state/vikix/used` and written by a whole-second timer when something changed and at `*quit-hook*`. What is kept is decided in one function, `vikix-used-what`: names only (a typed command without what followed it, nothing a script asked for, never a window's title). A new kind of thing to count goes there and into `KINDS` in `bin/vikix-used`; anything that could hold the user's own words must not. `tests/used.sh` checks that a title and typed words stay out of the file.

**The palette** (`bin/vikix-palette`, Super+Space; the end of `help.lisp`). rofi's combi mode over a script mode and `drun`: the script asks the desktop once for its rows (`vikix-palette-lines`: KIND, ID, WORDS, MORE, tab-parted) with a second and a half to answer, adds the projects, and hands a pick back as `(vikix-palette-run KIND ID)`, which runs it from a timer so a command that asks something doesn't hold `vikix eval`. A new kind of thing to find is a few lines in each of the two.

**Rescue** (`config/stumpwm/vikix/rescue.lisp`, `bin/vikix-rescue`). StumpWM does everything in one thread; when it goes round on something, nothing in that thread can say so. So: a timer notes a beat every two seconds; a watcher thread compares the beat with the main thread's processor time (`/proc/self/task/TID/stat`): no beat and busy is stuck (report, notification, then easing and a fresh loop by itself), no beat and idle is a menu open (nothing done). A third thread grabs Super+Ctrl+Alt+Escape on an X connection of its own. `vikix rescue` talks to Swank without `vikix-eval-for-agent`, so a worker thread answers. Code for those threads keeps to reading Lisp state, plain `setf`s and `interrupt-thread`: never an X request on StumpWM's connection. `bin/vikix-lock` raises i3lock's window twice a second: with a compositor i3lock is never told it's covered. `tests/rescue.sh` makes a hidden desktop spin; like every hidden-screen test it sets a dead `DBUS_SESSION_BUS_ADDRESS`, stands in for `notify-send` and `dunstctl`, and ends only its own processes by number (a test once left the real desktop's notifications paused).

**Plugins** (`bin/vikix-plugin`, `config/stumpwm/vikix/plugins.lisp`) come from their own repo, github.com/vukini/vikix-plugins (`~/src/vikix-plugins` on the dev machine), kept at the commit pinned in `bin/vikix-plugin` in `~/.local/share/vikix/plugins`; moving the pin is a Vikix release, after trying the new commit (`VIKIX_PLUGINS_REPO=~/src/vikix-plugins VIKIX_PLUGINS_COMMIT=$(git -C ~/src/vikix-plugins rev-parse HEAD) vikix plugin sync`). The user's plugins are named in `~/.config/vikix/plugins.list`; their Lisp loads through `vikix-load-file`, so errors ask; they get `vikix-plugin-bar` (the bar's `%P`), `vikix-plugin-key` and `vikix-plugin-menu` (its third argument is the entry's section of Super+m). What plugins find goes in the record store, `vikix records` (`bin/vikix-records`): one SQLite file, `~/.local/share/vikix/records.db` (600, WAL), table `records` (plugin, kind, key, at, title, body, data JSON, link) with an FTS5 index; plugins write with `vikix records add` (JSON on stdin; the same plugin, kind and key updates), and agents read it through `vikix mcp`'s read-only `records_search` and `records_get`.

**Live WM access.** `vikix eval '(form)'` (`bin/vikix-eval`, Python) runs Lisp in the running StumpWM, in the `STUMPWM` package. Its first road is Vikix's own socket (`config/stumpwm/vikix/socket.lisp`, loaded last): `$XDG_RUNTIME_DIR/vikix.sock` (`VIKIX_SOCKET` names another), 0600, served by the thread `vikix-socket`, a thread `vikix-socket-client` a request; one request a connection (`eval door|me FROM`, the forms, the client's writing side shut; back a status line, `ok`/`error`/`held`/`missing-door`, then the output). A text whose forms only read Lisp state (`vikix-socket-read-only-p`: the door's walker with `*vikix-door-allowed*` less `*vikix-socket-acts*` and `*vikix-door-no-extras*`) goes to the main thread first, so the answer follows what the desktop was doing (the key just pressed), and waits in slices (`vikix-socket-in-main`, `*vikix-socket-read-wait*`): after a slice with no answer in which the main thread used no processor time (`vikix-main-ticks`, rescue.lisp: a menu, a prompt, a program waited on; StumpWM's menu loop never serves the request channel), the request is cancelled and the client's thread evaluates the read itself, so the palette and `vikix what` are answered while a menu is open; a main thread that was working gets another slice, up to the deadline. Anything else goes to the main thread through `vikix-eval-for-agent` with its deadline (`:busy` back when it passes), and an agent's forms pass `vikix-eval-door` (swank.lisp, shared) in the thread first. The thread never makes an X request. **A test's StumpWM never serves the desktop's path:** `vikix-socket-path` serves only `VIKIX_SOCKET` when `VIKIX_SWANK_PORT` is set (every test sets it, the session never), and `bin/vikix-eval` asks only `VIKIX_SOCKET` then too, so the isolation line keeps tests off the live socket as it keeps them off the live Swank; `tests/lib/wm.sh` sets `VIKIX_SOCKET` to the test's folder. `vikix eval --socket` and `--swank` choose a road; `vikix doctor` asks the socket. `tests/socket.sh`. Swank stays beside it, for SLIME in Emacs and `vikix rescue`: it listens on `127.0.0.1:4004`. It has a password, `~/.slime-secret` (made by `40-config`), sent raw as the first packet, as SLIME does; `swank-guard.lisp` keeps a wrong password from killing Swank's accept thread. The Windows VM is on the NAT bridge virbr0 (0.41.0), so it can't reach 127.0.0.1; before that it was on passt, which maps the guest's gateway to host loopback, which is why Swank got its password. Still, any new local service should authenticate, and never go on passt. `drop_keys` (lib/common.sh) clears API keys from the environment in the installer and `vikix update`.

**Snapshots of the user's files.** `vikix snapshot/changes/history/undo` keep a separate git repo at `~/.local/state/vikix/yours.git` whose work tree is `$HOME`, limited to `config/yours.list`. `vikix agent` snapshots before starting Claude Code.

**The installed agent's skill.** `config/claude/skills/vikix/` is linked to `~/.claude/skills/vikix` on installed machines and guides Claude Code running *on* a Vikix desktop (OpenCode reads it there too). It is a first page and a page a subject. `SKILL.md`, the first page, is all an agent is sure to have read, so it holds what must always hold (whose files are whose, the snapshot, `vikix eval`, the short forms, and every *never*: secrets, the things that end the desktop, the user's things) and a table of the pages; **keep it under 16 KB** (it was 80, carried by every session), and when a new feature brings a rule that guards a secret or the desktop, the rule goes on the first page and the rest on the subject's page (`desktop.md`, `rules.md`, `keys.md`, `programs.md`, `system.md`, `ai.md`, `editors.md`, `projects.md`, `fixing.md`; a new page starts with the same line as the others and is named in the first page's table by its full path, `~/.claude/skills/vikix/NAME.md`, which is what lets the other agents open it). `bin/vikix-agent --write-guide` (40-config, and every `vikix agent`) turns the first page into `~/.local/share/vikix/AGENTS.md` for the other agents (Codex, Gemini, Aider), so it stays the one source. Update the pages when commands, keys or file ownership change. The list of keys, in `keys.md`, is not written by hand: `lib/skill-keys.sh --write` makes it from `registry.lisp` (grouped as the key card), with the commands an agent may run, and from the plugins at the pin, between the `<!-- keys -->`, `<!-- commands -->` and `<!-- plugin-keys -->` markers; run it after changing a command, a key or the plugins' pin. The same run writes `README.md`'s table of keys (between its `<!-- readme-keys -->` markers: a row a key, under the key card's groups), and `--check` fails when either is out of step. `tests/agents.sh` fails when the list is out of date, when any page's prose names a key that isn't in it, when the first page grows past 16 KB or loses one of its rules, or when a page isn't named there. Super+m shows each entry's key by itself (from `*vikix-bindings*`), so a menu label never names a key. **Super+m is in sections** (`commands.lisp`, `vikix-run-sections`): it opens on a row a section (`vikix-menu-sections`: an entry's fourth element; a plugin's that names none is in Plugins, anything else in Yours; `*vikix-apps-menu*`'s programs are in Apps), each row saying what the section holds (`vikix-menu-hint`, made from the labels up to their colon: `vikix-menu-head`), a section of one entry being that entry; inside a section lines with one head stay together, so a plugin's `Projects: ...` sits under Vikix's; typing at the top shows the entries of every section that match instead (`vikix-menu-row-shown-p`, the menu's filter, which is why `vikix-menu-pick` makes StumpWM's `single-menu` itself rather than call `select-from-menu`). A new entry's label should start with what it is about (`Screens: save this layout`). `vikix-run-menu` is still the plain menu, for the small ones (Power, Dropbox, the user's own). `tests/menu.sh` has the sections without a screen, `tests/registry.sh` the keys in a real StumpWM.

## Conventions

- **Keys keep one rule** (the head of `config/stumpwm/vikix/keys.lisp`; the user's guide: `docs/customize.md`, "The rule for keys"). Super: everyday (the six main apps, the small tools, focus, what is done to the window). Super+Shift: the same key moving the window, or its other way. Super+Alt: open something else, so every other app, every web app (`bin/vikix-webapp` takes no other key) and every plugin key. Super+Ctrl: switch something on the desktop. A new key is written with its command in `registry.lisp` (`:key`), where the rule puts it, with its command in `*vikix-key-everyday*`, `*vikix-key-switches*` or `*vikix-key-movers*` when it is one of those; `tests/lisp.sh` fails on one of Vikix's keys that breaks the rule (`vikix-key-problems`, `help.lisp`), `vikix doctor` names a plugin's, a web app's or the user's. A key taken away from Vikix goes into `*vikix-retired-keys*`, so a running desktop lets it go at the reload. Never write Shift+digit as a key name: it differs by keyboard layout (`vikix-bind-workspace-keys` asks the keyboard). After changing keys, `lib/skill-keys.sh --write` remakes the skill's list.

- Scripts: `set -euo pipefail`, print with `say`/`warn`/`die`, check `pkg_installed` before installing. Watch `pipefail` with assignments from pipelines that may legitimately fail (add `|| true`). Scripts run directly must be executable in git (`100755`).
- Comments explain *why* (Void quirks, ordering reasons), in plain short sentences. README.md is written the same way, with a table row per stage and per package list; keep it in step with the code.
- Releases (`.claude/release` does all of it; see Working in parallel): bump `VERSION`, commit as `Vikix X.Y.Z: <summary>`, and tag `vX.Y.Z`. Bump the last number (0.71.1 → 0.71.2) for every release, features included; it can go past 9 and on to 100 and beyond. Bump the middle one only when Vid asks (`.claude/release --middle`: 0.71.266 → 0.72.0), and never go to 1.0 on your own. Tags then sort properly only with `git tag --sort=v:refname`. The user pushes from their own terminal, since their SSH key needs a passphrase that Claude Code's shell can't supply. Tell them the shortcut from their `~/.bashrc`, not raw git: `gup` (push commits and tags, then `vikix update core` into `~/vikix`: Vikix only, in seconds; the usual step after a release. A plain `vikix update` brings Void and the tools, cargo too, and is run now and then), `gtry` (`vikix update core --from ~/src/vikix`: the desktop takes this repo's main straight from here, without GitHub or the passphrase, in a few seconds; for trying a small change, such as a lesson, before pushing; `gup` later pushes the same commits; a desk's unreleased work goes on the desktop with `vikix try` instead), `gpush` (push this repo and `~/.emacs.d`, tags included, without updating), `gall` (also `~/.dotfiles`); `gpl` pulls. On the dev machine these go through the `repos` plugin, which knows every project: `repos push` (pinned projects, Esploro and the plugins, before Vikix, and never a pin GitHub hasn't got), `repos pull`, `repos ship` (what `gup` runs: push, then `vikix update core`), `repos update` (the whole system); `repos` alone says what each needs, including commits past Vikix's pin. To see whether GitHub has anything new without the key, fetch over HTTPS: `git fetch https://github.com/vukini/vikix.git main:refs/remotes/origin/main`.
- Void specifics: runit services are enabled by symlinking `/etc/sv/<name>` into `/var/service/`; xbps repository overrides go in `/etc/xbps.d/` (same filename as in `/usr/share/xbps.d/`); `xbps` must be updated before other installs on a fresh system.
